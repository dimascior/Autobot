## Binding grammar

**Binding set.** BindingSet(record) = common_bindings ∪ the bindings of every conditional rule whose complete when predicate holds for the record. Rules add up: a record that matches several rules inherits the bindings of all of them. A record is immutable after commitment (R-2), so its set is fixed when it is produced, and every transition that later consumes it sees that same set.

**Rules.** Binding rules, each {when, provenance, bindings, open}. Within one rule, every selector in when must hold (AND), and a list of values in one selector means any of them. Across rules, every rule that holds contributes its bindings. A rule with no bindings records explicitly that it adds nothing. An open rule is one whose bindings Chapter 0 leaves open; it cites the unknown that asks.

**Partitions.** Rules conditioned on the same selectors form one partition: obj-30 has a path partition and a finalization_class partition, and obj-26 one partition on path, effect and effect_result. Within each partition every Chapter 0 context of the record resolves to exactly one rule; across partitions the matches add up (inventory.contexts). So an RO AcceptanceReceipt matches the RO rule and the READ_ONLY rule, and inherits both.

**Provenance.** The Chapter 0 transitions a rule covers: those that mint, prove or consume the record in a context its when clause matches. t-s16 proves the SL canonical commit, and t-s20 later consumes that receipt without performing the effect. Provenance is not a selector and not a wire field: it never decides whether a rule holds, so a record's bindings never depend on which transition consumes it. Where a rule lists it, the list is exact (inventory.provenance).

| Selector | Meaning |
|---|---|
| path | a finalization path or path group (transitions.json paths) |
| effect | the effect the record is the receipt or the intent of (transitions.json effects). For a receipt this is the effect it records, as the transition that established the receipt says; a later consumer such as t-s20 doesn't perform it. |
| effect_result | what happened to that effect (effect_results); not an EffectIntent state |
| kind | a record kind of a multi-kind object |
| finalization_class | the contract's finalization class |

## Golden vectors

The golden-vector plan for INV-05 (CH1-golden-digest-stability), plus predicate tests for the other inherited Chapter 1 tests. A golden vector is a valid record used as a fixture for the hash function; it need not be an admission that could happen, and no vector invents an object a cross-field rule forbids. A tier-effect vector's expected tiers are derived by the checker from identity.json: a tier changes when one of its own fields changes, or when a tier it embeds changes. No bytes or hashes are frozen in Phase A. Every exact fixture waits on fixture_waits_for_all. It is a full record, so it also waits on the unknowns of the fields it leaves unchanged; a vector's own list names only the unknowns open on the fields it changes, and anything else it needs.
